# CareerPilot CN V2/V3 正式版缺口审计

> 审计日期：2026-07-29
> 审计范围：V0–V3 中国校招主流程
> 不在范围：V4 面试中心、V5 Offer/入职管理、上游仓库更新
> 仓库快照：`main@65004e0`，工作区包含尚未提交的本地改动

> 修复状态（2026-07-29）：本文保留的是修复前审计快照。P0-1 至 P0-5、P1-1 至 P1-4 已在独立分支 `codex/v2-v3-formal-release` 完成；实现映射和可复验命令见文末“修复结果”，完整证据见 `docs/career-pilot-cn-v2-v3-release-verification.md`。

## 1. 结论

当前实现不是“只差 V4/V5”。CandidateProfile v2、岗位/匹配模型、30% 定制计算、申请侧车等底层能力已经建立，但 V2/V3 的默认 Web 工作流、规则确认、安全边界、岗位简历管理、申请状态一致性和验收矩阵仍有正式版阻断项。

更准确的状态是：**核心数据层和确定性规则已有可用基础，面向普通用户的完整产品闭环尚未完成。** 在下列 P0 问题关闭前，不应把 V2/V3 标记为正式完成，也不应继续扩展 V4/V5。

## 2. 已经建立的基础

以下内容不是本轮缺口，后续修复应继续保留：

- `cn-campus` 中国校招默认配置。
- CandidateProfile v1 兼容读取、v2 显式迁移与迁移备份。
- 学历、专业、专业代码、届别、毕业时间、英语等级、证书、政治面貌和流动偏好的结构化模型。
- JobPosting、EligibilityAssessment、MatchReport 及其 JSON Schema。
- 资格通过、失败、未知三态及固定的 5 分制软匹配权重。
- 岗位、匹配结果和 Markdown 报告的原子化保存。
- 主简历/岗位简历哈希绑定、唯一事实改动比例和 30% 硬上限。
- 受限字段手工填写提示，以及身份证、家庭成员、完整住址不进入申请侧车。
- 中国招聘详细阶段到九种兼容状态的映射。
- `/api/run` 的结构化 `artifact` 事件。
- V4/V5 的静态预留入口和阶段字段。本审计不把它们视为已实现功能。

## 3. P0：正式版阻断项

### P0-1 默认首页仍沿用海外职位扫描和固定跟进逻辑

**现状**

- 首次使用文案仍描述“解析简历后扫描实时招聘市场”。
- 首页继续请求 `/api/whats-new` 和 `/api/followups`。
- 首页主要行动仍包含“发现新职位”“免费扫描”和固定跟进。
- 侧边栏虽然已调整为中国流程，但首页业务逻辑尚未同步。

**影响**

用户进入系统后仍会被引导到海外 ATS 扫描和固定跟进，而不是“建立事实档案 → 导入官网岗位 → 资格分析 → 网申准备”的中国默认主链。

**相关位置**

- `web/src/components/home/first-run-home.tsx`
- `web/src/components/home/today-dashboard.tsx`
- `web/src/app/page.tsx`

**完成标准**

- 首次使用只引导进入 `/profile`，完成事实、证据、结构化字段和主简历。
- 今日待办默认展示资料缺口、岗位截止时间、待确认资格规则、待确认简历改写、网申材料和中国详细阶段。
- 海外扫描、固定跟进和门户扫描只在高级功能区出现。

### P0-2 岗位结构和资格规则没有真正经过用户确认

**现状**

- 岗位分析页只能修改招聘单位和岗位名称。
- 学历、专业、专业代码、届别、英语、证书、地点等规则只能查看，不能逐条修改、删除、新增或确认。
- “确认并评估”按钮没有对应的规则确认状态或确认记录。
- 当前正则提取容易把描述性字段误当硬条件。例如普通“工作地点”会直接生成硬规则；英语等级中出现“优先”时也可能仍按硬条件处理。

**影响**

用户无法纠正 AI/正则提取错误，确定性核心可能基于未经确认的规则给出 `ineligible`。

**相关位置**

- `web/src/components/cn/job-analysis-workbench.tsx`
- `lib/careerpilot/job-core.mjs`
- `schemas/cn/job-posting.schema.json`

**完成标准**

- 岗位解析结果进入独立的“待确认”状态。
- 用户可以修改单位类型、岗位、岗位代码、届别、截止时间、地点以及每条资格规则。
- 每条硬规则必须保留招聘原文引用，并记录确认状态。
- “优先、建议、相关专业优先”等表述不得自动成为淘汰条件。
- 仅完成整份岗位确认后才能调用 `job-evaluate`。

### P0-3 AI 输出校验可以被最终评估接口绕过

**现状**

- `/api/cn/jobs/propose` 会调用 `job-proposal-validate`。
- `/api/cn/jobs/evaluate` 可以直接接收客户端提交的 `dimensions`、`strengths` 和 `gaps`。
- `careerpilot.mjs job-evaluate` 没有强制再次调用 `validateFitProposal`。
- `buildFit` 只过滤“已确认事实”，没有完整执行 `job_match` 用途和敏感级别白名单。
- 只有 Claude CLI 显式禁用了读写工具；其他 CLI 主要依赖提示词和临时工作目录，没有统一的强制无工具策略。

**影响**

绕过建议接口直接调用评估接口时，可以提交未经 Schema/事实白名单校验的软匹配数据；非 Claude CLI 的“AI 不得写文件”边界也没有由应用统一强制执行。

**相关位置**

- `web/src/app/api/cn/jobs/propose/route.ts`
- `web/src/app/api/cn/jobs/evaluate/route.ts`
- `web/src/lib/clis.ts`
- `careerpilot.mjs`
- `lib/careerpilot/job-core.mjs`

**完成标准**

- `job-evaluate` 对任何外部提交的软匹配内容强制执行同一份 FitProposal Schema 和事实白名单校验。
- 敏感、受限、未确认或未授权 `job_match` 的事实无法进入软匹配和报告。
- 所有 CLI 使用明确的无工具/只读调用策略；无法做到时不得作为 Web AI 建议器启用。
- AI 进程使用最小环境变量，不继承无关凭据。

### P0-4 岗位简历工作流只实现了事实删减

**现状**

- 底层支持事实删除、增加、改写和顺序变化的比例计算。
- Web 端目前只能勾选保留或删除事实。
- 没有岗位改写建议、逐条接受/拒绝、排序操作或完整差异展示。
- 用户可以一键把“当前全部事实”直接保存为 `ready` 主简历，缺少正式预览确认。
- 岗位定制预览默认不保存，导出后也没有在“主简历和岗位简历”页面统一列出岗位变体。

**影响**

30% 核心虽然存在，但用户无法完成计划要求的“证据约束改写 → 逐条确认 → 预览 → 导出 → 后续管理”。

**相关位置**

- `web/src/components/cn/resume-tailoring-panel.tsx`
- `web/src/components/cv-editor.tsx`
- `web/src/app/api/cn/resumes/baselines/route.ts`
- `web/src/app/api/cn/resumes/tailor-preview/route.ts`
- `lib/careerpilot/tailoring-core.mjs`

**完成标准**

- 主简历必须先预览并由用户确认，才能进入 `ready`。
- 岗位简历支持事实取舍、排序和事实 ID 约束的候选改写。
- 每条改写都必须有明确的用户确认状态。
- 页面展示改写前后、事实 ID、变化类型、唯一事实计数和总比例。
- 岗位变体及导出记录可在统一简历工作室中查看、重新打开和识别过期状态。

### P0-5 中国详细阶段和 Markdown 汇总仍可能不一致

**现状**

- 默认“申请进度”仍使用旧 `/pipeline` 页面，只读取 `data/applications.md`，不展示申请侧车的中国详细阶段。
- 旧 `/api/status` 只调用 `set-status.mjs`，不会同步申请侧车。
- `application-stage` 更新发现既有不一致时不会先拒绝，而是调用 `set-status` 覆盖 Markdown 状态，然后发布新的侧车。
- `set-status` 有锁，但申请侧车读—改—写没有共享锁；两个并发阶段更新可能覆盖事件历史。

**影响**

从旧进度页更新状态会制造侧车冲突；并发请求可能丢失详细阶段事件；现有实现不符合“发现冲突就报告，不静默覆盖”的要求。

**相关位置**

- `web/src/app/pipeline/page.tsx`
- `web/src/components/pipeline-view.tsx`
- `web/src/app/api/status/route.ts`
- `lib/careerpilot/application-core.mjs`

**完成标准**

- 默认申请进度页读取并显示申请侧车详细阶段。
- 所有 Web 状态更新统一进入同一个“侧车 + 汇总”锁定事务路径。
- 更新前先校验一致性；发现冲突返回 409，并展示双方状态，不自动选择一方覆盖。
- 同一申请的并发阶段更新串行化，事件历史不可丢失。
- 旧 `/api/status` 对存在中国申请侧车的记录必须转发到统一路径或拒绝直接更新。

### P0-6 官网 URL 导入和来源可靠性判定不足

**现状**

- URL 导入使用服务端 `fetch` 和 HTML 标签清理，不执行浏览器渲染。
- 动态招聘官网、脚本加载正文、跳转确认页等场景可能无法读取。
- 任何公开 HTTP(S) URL 都会被标为 `official_url`。
- `official_url` 的来源可靠性上限为 5 分，但没有验证域名是否属于招聘单位或其正式招聘平台。

**影响**

常见央国企动态招聘页面可能导入失败，第三方转载页也可能被错误赋予最高来源可靠性。

**相关位置**

- `web/src/app/api/cn/jobs/parse/route.ts`
- `lib/careerpilot/job-core.mjs`

**完成标准**

- URL 导入采用浏览器渲染优先、受限 HTTP 回退的抓取路径。
- 保存最终 URL、重定向链、抓取时间和页面标题。
- “官方来源”必须由用户确认或通过可解释的单位域名/招聘平台证据确认。
- 未确认来源不得自动获得 5 分可靠性。

## 4. P1：功能完整性欠账

### P1-1 网申材料更接近固定模板，而不是岗位材料准备器

- 字段集合和字数限制主要为固定值，没有从具体公告或网申页面提取。
- 应聘动机、自我评价默认留空，没有生成引用事实 ID 的候选草稿。
- 经历字段只是拼接已确认事实，缺少岗位相关排序和逐条来源展示。
- 材料检查表固定为成绩单、英语、奖励、身份证件和家庭信息，不能表达岗位特有材料。

**完成标准：** `application-prepare` 能接收岗位/表单字段定义，生成字段级事实引用、字数限制、缺失材料和待确认回答草稿；不得自动提交。

### P1-2 个人事实中心的 Web 能力落后于数据模型

- Schema 支持多个英语等级和资格证书，页面只维护数组第一项。
- 高风险证据只能填写 HTTPS 链接，不能上传成绩单、证书等本地证据文件。
- CandidateProfile v2 使用 `structured.political_status`，但简历渲染仍读取旧的 `candidate.political_status`，形成两套来源。
- 事实审核和结构化字段位于同一长页面，缺少清晰的完成度、缺失项和下一步引导。

**完成标准：** 多证书可增删，本地证据可安全导入并记录哈希，v2 输出只读取事实引用后的政治面貌，页面能明确显示建档完成度。

### P1-3 测试矩阵没有覆盖原计划的关键风险

当前测试数量较多，但以下计划场景仍缺失：

- 央企、地方国企、银行、运营商分别具备“通过、失败、信息不足”黄金 JD；当前主要验证单位分类。
- 真实可解析 PDF、真实 DOCX、10 MB 边界、路径穿越、符号链接、异常 ZIP/DOCX、超大解压内容和图片型文件。
- 岗位变化、Profile 变化和主简历变化后的过期预览测试。
- 申请侧车并发锁和冲突拒绝测试。
- 非 Claude CLI 无工具边界测试，以及直接调用 `job-evaluate` 的绕过测试。
- 受限信息对日志、API 响应、页面 HTML 和浏览器快照的统一扫描。
- 真实浏览器完整链路：匿名建档 → 导入 JD → 修改并确认规则 → 资格判断 → 报告 → 岗位简历逐条确认 → 导出 → 网申准备 → 阶段更新。

### P1-4 本地正式版尚未形成可回退基线

审计时仓库仍位于 `main@65004e0`，中文化和 V2/V3 改动均处于未提交工作区；`web/package-lock.json` 还包含无依赖变化的元数据噪声，二次开发计划也处于未跟踪状态。

这与上游仓库无关，但会影响本地正式版的可审查、可回退和后续继续开发。

**完成标准：** 清理无效 lockfile 噪声，确认现有文档归属，将 V2/V3 改动形成独立本地分支和可验证提交，并保留完整测试证据。

## 6. 推荐修复顺序

### 批次 A：先纠正默认产品主链

1. 重做首次使用页和今日待办。
2. 建立真正的岗位结构/规则确认编辑器。
3. 将默认申请进度切换到中国详细阶段视图。

### 批次 B：收紧安全与一致性边界

1. `job-evaluate` 强制验证 FitProposal。
2. 统一所有 CLI 的只读、无工具运行策略。
3. 为申请侧车和 Markdown 汇总建立共享锁和冲突拒绝机制。
4. 修复 URL 官方来源确认和动态页面读取。

### 批次 C：完成 V3 用户工作流

1. 完成主简历确认、岗位改写、排序、逐条确认和差异预览。
2. 建立岗位简历列表、过期提示和导出记录。
3. 完善网申字段、证据化回答草稿和岗位特有材料清单。
4. 完善个人事实中心的多证书和本地证据管理。

### 批次 D：补齐正式版验收与本地交付

1. 建立四类黄金 JD 矩阵和文件安全测试。
2. 增加 AI 绕过、隐私扫描、状态冲突和并发测试。
3. 完成真实 Playwright 全链路 E2E 和主要页面视觉检查。
4. 清理工作区并形成独立、可回退的本地正式版提交。

## 7. V2/V3 完成定义

同时满足以下条件后，才能把 V2/V3 标记为正式完成：

- 新用户从首页进入后不会被默认引导到海外扫描或固定跟进。
- 岗位结构和每条硬规则均经过用户确认，并保留招聘原文依据。
- 无论从哪个 API 入口进入，AI 内容都不能绕过 Schema、事实白名单和确定性资格核心。
- 主简历先确认，岗位简历所有改写逐条确认，超过 30% 无法导出。
- 网申材料具备字段来源、事实引用、字数限制、材料缺口和用户确认。
- 中国详细阶段与 Markdown 汇总使用同一锁定写入路径，冲突时拒绝而非覆盖。
- 原计划中的黄金 JD、文件安全、隐私、并发和真实浏览器 E2E 全部通过。
- 本地工作区形成独立、可审查、可回退的正式版提交。

| 原缺口 | 修复结果 |
